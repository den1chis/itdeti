# Выкладка на прод: пошаговая инструкция (ветки `lms-mvp`)

> **С ночи 4 выкладка автоматизирована.** Одна команда (PowerShell):
> `powershell -ExecutionPolicy Bypass -File D:\itdeti_learn\itdeti\scripts\deploy_night4.ps1`
> — preflight → counts → бэкап в `D:\itdeti_backups` → миграция 014 → postcheck → слияние и push `itdeti` → ожидание
> новой версии в `/health` → смоук сервера (при провале — `git revert` слияния) → `itdetiWeb` → `itdetiLearn` → counts.
> К прод-базе обращается только `scripts/prod_ops.py --prod` (секрет: `D:\itdeti_secrets\prod.env`, строка
> `PROD_DATABASE_URL=...`). Продолжить после остановки: `… deploy_night4.ps1 -FromStep N`.
> Откат и аварийная разблокировка входа: `docs/RUNBOOK_EMERGENCY.md`.
> Ниже — ручная выкладка 2026-11-11 (миграции 012–013), оставлена как справка.

Для кого: для человека без опыта выкладки. Делать по порядку, не пропуская проверок.
Время: 1,5–2 часа, в окно без занятий (Android-приложение может ненадолго терять связь с сервером).

**Порядок важен:** бэкап → миграции базы → переменные Render → код сервера (`itdeti`) → CRM (`itdetiWeb`) → ученический сайт (`itdetiLearn`).
Миграции раньше кода: новый код читает колонки `users.roles`, `lessons.teacher_id`, `students.teacher_id`; без миграций
перестанет работать вход в CRM и почти всё остальное. Код сервера раньше CRM: новая CRM вызывает новые маршруты.

Что где:
| Что | Где |
|---|---|
| Сервер API | Render, `https://itdeti.onrender.com` (бесплатный тариф, регион West US / Oregon, автодеплой с `main`) |
| База | Supabase, прод-проект (не `itdeti-dev`) |
| CRM | GitHub Pages, репозиторий `den1chis/itdetiWeb` |

Если что-то идёт не так — раздел 10 «Откат».

## 1. Бэкап базы
1. Supabase → **прод-проект** (проверьте название проекта вверху слева: не `itdeti-dev`) → **Database → Backups**.
   Если там есть свежая автоматическая копия (на платных тарифах — ежедневные), запомните её дату и время. На бесплатном
   тарифе скачиваемых копий может не быть — тогда обязателен пункт 2.
2. Выгрузка JSON (работает на любом тарифе): **SQL Editor → New query**, вставить содержимое `itdeti/scripts/prod_backup.sql`
   (из ветки `lms-mvp`), **Run**. Результат — одна ячейка `backup_query` с текстом второго запроса.
   - Скопировать ячейку целиком, открыть **новую** вкладку SQL Editor, вставить, **Run**.
   - Результат: по строке на каждую таблицу (`table_name`, `rows`, `data` — все строки в JSON).
   - Над результатом **Export → Download CSV**, назвать `itdeti_backup_2026-11-11.csv` (дата выкладки).
   - Ожидается: столько строк, сколько таблиц в базе (около 30); у `students`, `lessons`, `payments` поле `rows` не 0.
3. Где хранить: на своём компьютере в папке вне репозиториев + копия на личном облачном диске. **Не в чате, не в GitHub:**
   в файле данные учеников и родителей, хеши паролей, refresh-токены.

## 2. Проверка базы до миграций: `prod_preflight.sql`
SQL Editor прод-проекта → вставить `itdeti/scripts/prod_preflight.sql` → выполнять **по одному запросу**
(выделить блок от `-- [N]` до `;` → Ctrl+Enter). У каждого запроса в файле написано, что считается нормой.
Записать результаты (лучше скриншотами).

| Запрос | Норма | Если не так |
|---|---|---|
| [1] число таблиц | около 30 (на dev 33 вместе с `student_accounts`) | 0 или единицы — открыт не тот проект, **СТОП** |
| [2], [3] RLS | у всех `true`, запрос [3] — 0 строк | выкладке не мешает (сервер ходит ролью `postgres`), но таблица без RLS открыта через API Supabase — записать, чинить отдельной миграцией |
| [4] `user_role` | `admin, teacher, parent, student`, без `methodist` | `methodist` уже есть — не страшно |
| [5] новые объекты | все `false` | что-то `true` — миграции всё равно безопасны (`IF NOT EXISTS`), записать |
| [6] | 3 строки: `lessons, students, users` | меньше — **СТОП** |
| [7]–[10] `lms_*` | по `008`: 5 колонок у `lms_enrollments`, UNIQUE (student_id, course_id), `ON DELETE CASCADE`, 8 индексов | на dev расхождения есть: лишние колонки `start_date, weekday, lesson_time`, нет UNIQUE, все `NO ACTION`, нет индексов. Выкладке не мешает; записать — это вопрос на потом |
| [11] число строк | реальные числа школы | записать: после выкладки сравнить |
| [12] пользователи | 1 активный `admin` | `is_active` пустой (NULL) у вашей учётки — **СТОП**, сначала разобраться |

## 3. Миграции 012 и 013
Файлы — в ветке `lms-mvp` репозитория `itdeti`: `supabase/migrations/012_student_accounts.sql`, `supabase/migrations/013_access_model.sql`
(на GitHub: переключить ветку на `lms-mvp` → открыть файл → кнопка «Raw» → скопировать всё).
**Никогда не запускайте `001_reset_school_schema.sql`** — он удаляет все таблицы школы.

1. SQL Editor прод-проекта → New query → вставить **весь** `012_student_accounts.sql` → **Run**.
   Ожидается «Success. No rows returned». Ошибка — **СТОП**, ничего дальше не делать, прислать текст ошибки.
2. New query → вставить **весь** `013_access_model.sql` → **Run**. Ожидается «Success. No rows returned».
3. Проверка: вставить `itdeti/scripts/prod_postcheck.sql`, выполнять по одному запросу:
   - [1] все пять `true`; [2] `true`; [3] `0`; [4] у каждой строки `roles` = `{role}`; [5] `true`;
   - [6] три внешних ключа (`SET NULL`, `SET NULL`, `CASCADE`) и два индекса;
   - [7] все три числа `0`; [8] те же числа строк, что в шаге 2, запрос [11].
   Что-то не так — **СТОП**, код не выкладывать (старый код с новыми колонками работает: миграции только добавляют).

Повторный запуск 012 или 013 безопасен (проверено на dev: второй запуск ничего не меняет).

## 4. Ключ `STUDENT_PASSWORD_KEY`
Нужен, чтобы админ (и позже преподаватель) мог посмотреть пароль ученика. Ключ **новый**, не тот, что в dev `.env`.
1. На своём компьютере, в папке `itdeti` (где есть `.venv`):
   ```bash
   .venv/Scripts/python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
   ```
   Выводится строка из 44 символов, заканчивается на `=`.
2. Сохранить копию в **менеджере паролей** (запись «itdeti STUDENT_PASSWORD_KEY prod»). **Не в чате, не в заметках, не в репозитории.**
3. Потеря ключа = пароли учеников нельзя посмотреть, только сбросить (вход учеников при этом работает: он идёт по хешу).
   Смена ключа = все сохранённые пароли станут «недоступны для просмотра» (сервер ответит «сбросьте»), их нужно сбросить.

## 5. Переменные на Render
Render → сервис `itdeti` → **Environment**.

| Переменная | Значение | Зачем |
|---|---|---|
| `STUDENT_PASSWORD_KEY` | ключ из шага 4 | просмотр паролей учеников |
| `BEHIND_PROXY` | `true` | ограничение частоты входа учеников считает IP клиента, а не прокси Render |
| `TRUSTED_PROXY_HOPS` | `1` (проверить в шаге 9, п. 6) | сколько прокси дописывают адрес в `X-Forwarded-For` |
| `CORS_ORIGINS` | **не задавать** (по умолчанию `https://den1chis.github.io` + локальные адреса) | какие сайты могут обращаться к API из браузера |
| `CORS_EXTRA_ORIGINS` | не задавать (позже — адрес своего домена) | добавочные адреса |
| `ENABLE_DOCS` | **не должна быть задана** (или `false`) | иначе `/docs` и схема API открыты всем |
| `APP_ENV` | `production` (или не задавать: с ночи 3 это значение по умолчанию в коде) | **ни в коем случае не `development`**: при `development` сервер на старте сам создаёт таблицы мимо миграций, без RLS, и пишет все SQL-запросы в лог. Если на Render стоит `development` — исправить на `production` |
| `DISABLE_SCHEDULER` | не задавать / `false` | фоновых задач в коде сейчас нет; переменная на будущее |

Остальные переменные (`DATABASE_URL`, `JWT_SECRET_KEY` и т. д.) уже есть — не трогать.

Также проверить: Render → сервис → **Settings → Build & Deploy → Docker Command / Start Command** — поле должно быть **пустым**
(тогда используется команда из `Dockerfile`: `uvicorn main:app --host 0.0.0.0 --port ${PORT:-8000}` — порт из переменной `PORT`, которую задаёт Render, без `--reload`). Если там своя команда — записать её;
`--proxy-headers --forwarded-allow-ips='*'` там быть **не должно** (подделка IP).

Сохранить переменные: **Save Changes** (Render может предложить «Save, rebuild and deploy» — можно, код пока старый; новые переменные он просто не читает).

## 6. Код сервера: слияние `lms-mvp` → `main` в `itdeti`
Render сам выложит `main` (автодеплой).

Вариант A — через GitHub:
1. Сначала отправить ветку (из папки `itdeti` на своём компьютере):
   ```bash
   git push origin lms-mvp
   ```
2. github.com/den1chis/itdeti → **Pull requests → New pull request** → base: `main`, compare: `lms-mvp` → **Create pull request** → **Merge pull request** → **Confirm merge**.

Вариант B — командами:
```bash
git checkout main
git pull origin main
git merge --no-ff lms-mvp
git push origin main
git checkout lms-mvp
```

Дальше:
1. Render → сервис → **Events / Deploys**: новый деплой, статус «Live» (обычно 3–6 минут). «Failed» — раздел 10.
2. Проверки (в браузере):
   - `https://itdeti.onrender.com/health` → `{"status":"ok","env":"production"}` (в `env` — значение `APP_ENV`).
   - `https://itdeti.onrender.com/docs` → `{"detail":"Not Found"}` (404). Если открылась документация — `ENABLE_DOCS` задана, убрать.
   - `https://itdeti.onrender.com/openapi.json` → тоже 404.
3. Вход админа в CRM (старая CRM ещё на GitHub Pages — она работает с новым сервером): войти, открыть Главную, Календарь.
   В консоли браузера (F12 → Console) не должно быть ошибок `CORS`.
4. `/auth/me`: в CRM F12 → Network → запрос `me` → ответ 200 с Вашей ролью `admin`.

## 7. CRM: слияние в `itdetiWeb`
Как в шаге 6 (вариант A или B), в репозитории `itdetiWeb`. GitHub Pages обновится за 1–2 минуты
(репозиторий → **Actions** → «pages build and deployment» зелёный).
1. Открыть CRM, **жёсткое обновление**: на компьютере Ctrl+Shift+R (Mac: Cmd+Shift+R). На телефоне — закрыть вкладку и открыть снова.
2. Проверить, что загружена новая версия: F12 → Network → обновить → файлы `app.js?v=2026111101`, `lms.js?v=2026111101`, `student-access.js?v=2026111101`.
3. «Курсы → Ученики → карточка ученика» — внизу блок «Доступ к ученическому сайту». В старой карточке (вкладка «Ученики», форма с ценой) блока больше нет.

## 8. Ученический сайт: новый репозиторий `itdetiLearn`
1. github.com → **New repository** → имя `itdetiLearn`, **Public**, без README/.gitignore/лицензии (пустой) → **Create repository**.
2. На своём компьютере, в папке `itdetiLearn`:
   ```bash
   git checkout -b main
   git remote add origin https://github.com/den1chis/itdetiLearn.git
   git push -u origin main
   ```
   (`git checkout -b main` создаёт ветку `main` из текущей `lms-mvp`; если ветка `main` уже есть — `git checkout main && git merge lms-mvp`.)
3. Репозиторий → **Settings → Pages** → Source: **Deploy from a branch** → Branch: `main`, папка `/ (root)` → **Save**.
4. Через 1–2 минуты открыть `https://den1chis.github.io/itdetiLearn/` → экран «Вход для учеников».

## 9. Smoke-проверки
1. CRM (компьютер): Главная, Календарь (неделя, месяц), Финансы (сводка, операции), Задачи, Курсы (каталог, урок) — открываются, числа как вчера.
2. Android-приложение: открыть, убедиться, что CRM в нём загружается и Вы вошли; дождаться (или вызвать) уведомление Kaspi/WhatsApp — оно появилось в «Уведомлениях»; виджет на рабочем столе обновляется.
   Если в приложении ошибка связи, а в браузере всё работает — вероятно, WebView грузит CRM не с `https://den1chis.github.io`;
   временно добавить адрес в `CORS_EXTRA_ORIGINS` на Render (см. раздел 10).
3. Тестовый ученик (только на нём, не на настоящих учениках):
   - CRM → Ученики → создать «Тест Тестов» (цена любая, например 1).
   - Курсы → Ученики → «Тест Тестов» → «+ Назначить курс».
   - В той же карточке: «Доступ к ученическому сайту» → «Создать доступ» → показан логин и пароль.
   - С телефона открыть `https://den1chis.github.io/itdetiLearn/`, войти → курс → урок → «✓ Урок пройден».
   - В CRM: «Показать» → пароль виден → «Скрыть».
   - На телефоне 5 раз неверный пароль → «Вход заблокирован на 15 минут».
   - В CRM обновить карточку → «вход заблокирован до …» → «Снять блокировку» → на телефоне вход с верным паролем работает.
4. Ограничение частоты за прокси (проверка `TRUSTED_PROXY_HOPS`), с компьютера в терминале (Git Bash), логин заведомо несуществующий:
   ```bash
   for i in $(seq 1 11); do curl -s -o /dev/null -w "%{http_code} " -X POST https://itdeti.onrender.com/student/auth/login -H "Content-Type: application/json" -H "X-Forwarded-For: 10.0.0.$i" -d '{"login":"nobody-check","password":"000000"}'; done; echo
   ```
   Ожидается: десять `401` и одиннадцатый `429` (подделанный адрес не помогает обойти лимит).
   Затем **сразу** с телефона через мобильный интернет (другая сеть) войти тестовым учеником — должно пустить.
   > **С ночи 4** IP берётся из `CF-Connecting-IP` (Cloudflare), `TRUSTED_PROXY_HOPS` нужен только как запасной вариант.
   > Ниже — разбор ночи 3; совет «оставить `BEHIND_PROXY=false`» больше **не применять**: это отключит
   > `CF-Connecting-IP` и вернёт одну общую корзину на всю школу (CRM и ученический сайт).
   - (ночь 3) Одиннадцатый ответ тоже `401` → значение `TRUSTED_PROXY_HOPS` слишком большое (берётся подделываемый адрес): поставить `1`.
   - (ночь 3) С телефона в другой сети тоже «Слишком много попыток» → все клиенты попадают в одну корзину: поставить `TRUSTED_PROXY_HOPS=2`, сохранить (Render перезапустит сервис), повторить оба теста.
   По документации Render весь трафик идёт через Cloudflare, который **дописывает** адрес клиента в конец `X-Forwarded-For`;
   на проде 2026-11-11 правый адрес оказался внутренним `10.x`, меняющимся от запроса к запросу — поэтому в ночь 4 перешли на `CF-Connecting-IP`.
5. Удалить тестового ученика (Ученики → «Тест Тестов» → Удалить) — он станет неактивным; его доступ выключить в карточке доступа.

## 10. Откат
- **Сервер:** Render → сервис → **Deploys** → предыдущий успешный деплой → **Rollback** (кнопка у деплоя). Через 2–5 минут работает старый код.
  Миграции откатывать **не нужно**: они только добавляют колонки и таблицу, старый код их не замечает.
  Потом вернуть `main` к прошлому состоянию: на GitHub открыть смерженный Pull request → **Revert** → Merge (иначе следующий автодеплой выложит то же самое).
- **CRM:** github.com/den1chis/itdetiWeb → смерженный Pull request → **Revert** → Merge (или командами `git revert -m 1 <коммит слияния>` в `main` и `git push origin main`). Pages обновятся за 1–2 минуты; жёсткое обновление страницы.
- **Ученический сайт:** Settings → Pages → Source: **None** (сайт перестанет открываться), либо просто не раздавать адрес.
- **CORS сломал Android-приложение:** Render → Environment → `CORS_EXTRA_ORIGINS` = адрес, с которого грузится CRM в WebView (виден в ошибке консоли/логах), Save. Крайний вариант — откат сервера.
- **Тестовые данные:** удалить «Тест Тестов» (или оставить неактивным).
- **Логи:** Render → сервис → **Logs**. Искать строки `Traceback`, `ERROR`, `LMS module failed to load`, `Student site module failed to load`,
  `Teacher/staff module failed to load` (модуль не загрузился, остальное API работает), `password_view_disabled` (нет ключа).

## 11. Render: бесплатный тариф
- По документации Render (FAQ, проверено 2026-11-10): бесплатный веб-сервис **засыпает после 15 минут без входящих запросов**
  и просыпается при следующем запросе примерно за минуту. Также на бесплатном тарифе 750 часов работы в месяц на рабочее пространство.
- Вы отмечали, что расписание обращается к серверу примерно каждые 30 минут. Это реже, чем 15 минут, поэтому сервер всё равно может засыпать между обращениями; первый вход ребёнка после паузы может ждать до минуты.
- Варианты: платный тариф (Starter и выше не засыпают) — надёжно; внешний пинг `/health` раз в 10–14 минут (например, бесплатный монитор доступности) — работает, но расходует часы бесплатного тарифа и против духа бесплатного тарифа.
- Регион Render — **West US**. Если база Supabase в другом регионе, каждый запрос идёт через континент (задержка); при выборе тарифа стоит держать их в одном регионе.

Источники: https://render.com/docs/faq, https://render.com/articles/how-render-handles-ddos-attacks, https://render.com/articles/host-pocketbase-on-render
