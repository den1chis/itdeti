# Аварийные действия (ночь 4)

Коротко: что делать, если после выкладки ночи 4 что-то пошло не так. Подробная выкладка — `docs/DEPLOY_RUNBOOK.md`,
инструмент — `scripts/prod_ops.py`.

## 1. Не пускает в CRM: «Слишком много попыток входа»
Как работает ограничение (`core/login_guard.py`):
- 5 неверных паролей подряд с одного адреса (IP) для одного email → эта пара «email + IP» заблокирована на 15 минут.
  С другого IP (мобильный интернет вместо Wi-Fi) вход тем же email работает.
- 30 неверных паролей за 15 минут по одному email с любых адресов → вход этим email закрыт на 15 минут для всех IP,
  кроме тех, с которых за последние 30 дней был успешный вход.
- Больше 10 попыток входа в минуту с одного IP → минута ожидания (хранится в памяти сервера, сбрасывается сама).

Самое простое — подождать 15 минут или войти через другую сеть. Если ждать нельзя:

**Supabase → прод-проект (не `itdeti-dev`) → SQL Editor → New query**, вставить (заменив `ВАШ_EMAIL`), **Run**:

```sql
DELETE FROM auth_login_state WHERE email = lower(trim('ВАШ_EMAIL'));
DELETE FROM auth_email_locks WHERE email = lower(trim('ВАШ_EMAIL'));
```

Это снимает все блокировки этого email (и по парам, и общую). Таблицы служебные: в них только счётчики попыток,
данных школы нет. После этого вход с верным паролем работает сразу.

Снять вообще все блокировки (всех email):

```sql
DELETE FROM auth_login_state;
DELETE FROM auth_email_locks;
```

**Важно перед сменой пароля CRM.** Android-приложение входит email и паролем, которые зашиты в само приложение
(`D:\itdetiApp`). После смены пароля в CRM телефон продолжит слать старый — раз в 5 минут и при каждом уведомлении —
и через 5 попыток заблокирует пару «Ваш email + IP Вашего Wi-Fi» на 15 минут, по кругу. Тогда из этой сети не войти
и в CRM с верным паролем. Порядок: сначала пересобрать приложение с новым паролем (а лучше — перевести его на
отдельную учётку или токен), потом менять пароль; если уже случилось — выключить уведомления приложения/телефон из сети
и выполнить SQL ниже.

Посмотреть, кто и откуда подбирал пароль: CRM → «Журнал» → фильтр «Вход: неверный пароль» / «Вход: блокировка»,
или SQL:

```sql
SELECT created_at, action, ip, details->>'email' AS email
FROM audit_log
WHERE action IN ('login_failed', 'login_locked')
ORDER BY created_at DESC
LIMIT 50;
```

## 2. Откат сервера
1. Render → сервис `itdeti` → **Deploys** → предыдущий успешный деплой → **Rollback**. Через 2–5 минут работает старый код.
2. Вернуть `main`, иначе следующий автодеплой выложит то же самое:
   ```bash
   git checkout main
   git pull origin main
   git revert -m 1 <коммит слияния «Merge lms-mvp: night 4 …»>
   git push origin main
   git checkout lms-mvp
   ```
3. Миграцию `014_security.sql` откатывать **не нужно**: она только добавляет три таблицы и колонку
   `refresh_tokens.token_hash`; старый код их не замечает.
4. Что почувствуют пользователи при откате сервера: сессии CRM, выданные **новым** сервером (вход или обновление
   токена после выкладки), старый сервер не найдёт (он ищет токен в открытом виде) — CRM один раз попросит войти заново.
   Android-приложение входит по логину и паролю и refresh-токены не использует — его откат не затрагивает.

## 3. Откат CRM и ученического сайта
```bash
git checkout main
git pull origin main
git revert -m 1 <коммит слияния>
git push origin main
git checkout lms-mvp
```
в `itdetiWeb` (и в `itdetiLearn`, если нужно). GitHub Pages обновится за 1–2 минуты; в браузере — жёсткое обновление
(Ctrl+Shift+R). Старая CRM работает с новым сервером (страницы «Журнал» в ней просто нет).

## 4. Восстановление данных
Миграция 014 данные школы не меняет. Бэкап перед выкладкой: `D:\itdeti_backups\itdeti_backup_<дата>_<время>.json`
(все таблицы `public`, по таблице: `rows` и `data`). Файл содержит персональные данные и хеши паролей — не отправлять
в чат и не класть в репозиторий.
